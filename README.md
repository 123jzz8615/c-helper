# 竞途 AI 项目详细分析

> 版本：2026-08-25  
> 用途：项目申报、路演介绍、活动复盘、团队评审与后续用户验证规划  
> 项目阶段：可运行的技术 MVP，尚处于真实用户验证和商业验证之前

---

## 一、项目摘要

### 一句话项目介绍

> **竞途 AI 是一款面向算法竞赛与编程入门学生的个性化学习助手，根据学习目标、当前基础、可用时间和错题表现生成每日学习计划，并串联课程、洛谷练习、错题复盘与学习报告。**

### 路演短版

> **竞途 AI 不再让学生凭感觉决定“今天学什么”，而是让每一次练习自动影响下一步学习。**

### 项目成熟度判断

当前项目已经完成了从注册、诊断、推荐、课程、刷题记录、错题复习到学习报告的端到端闭环，适合称为“可运行的技术 MVP”。

但以下能力尚未得到充分验证：

- 是否真的能够提升学生的学习效率或学习成绩；
- 学生是否愿意持续使用；
- 推荐结果是否比固定课程路线更有效；
- 学生、家长、学校或培训机构是否愿意付费；
- 生成式 AI 是否会成为用户愿意付费的核心价值。

因此，项目当前最重要的下一步不是继续堆叠功能，而是通过真实用户测试验证“学生是否更容易开始学习、是否减少重复错误、是否愿意持续回来”。

### 事实、推断与目标的口径

本文采用以下标记：

- **[已实现]**：可以从代码、数据库结构或现有测试中直接确认。
- **[合理推断]**：根据产品设计可以推测，但尚无真实用户数据证明。
- **[待验证]**：需要通过访谈、可用性测试、留存数据或付费测试确认。
- **[30 天目标]**：活动后计划达成的目标，不代表当前已经完成。

## 二、详细解释

### 2.1 用户问题

算法学习不缺少题目、课程、视频和题解，真正缺少的是一个能够持续回答以下问题的系统：

1. 我今天应该学什么？
2. 为什么现在应该学这个？
3. 这节内容是否符合我的基础和目标？
4. 做错以后，我下一步应该复习什么？
5. 我本周的学习时间是否足够完成目标？
6. 我是知识不会、算法不会，还是代码实现出了问题？

传统学习路径通常是固定目录，题库通常只负责出题，视频平台通常只负责提供内容，错题本通常只是收藏夹。它们之间缺少一个持续更新的学习调度层。

竞途 AI 的产品定位正是连接这些环节：

> **把学习目标、学习时间、基础诊断、课前反馈、练习结果和错题原因，转化成下一步可执行的学习安排。**

### 2.2 目标用户

#### 核心用户

- 零基础至“准备竞赛”阶段的学生；
- 使用 C、C++ 或 Python 学习编程和算法的人；
- 准备蓝桥杯、CSP-J/S、洛谷入门或学校考试的人；
- 每周可投入时间有限、需要明确优先级的人；
- 已经开始刷题，但缺乏稳定路线和复习习惯的人；
- 会在洛谷、Bilibili、抖音、博客和题解之间寻找资料的人。

#### 目标场景

| 场景 | 用户任务 | 产品支持 |
|---|---|---|
| 竞赛备考 | 在有限时间内优先学习高价值知识点 | 目标权重、截止日期和每日预算 |
| 编程入门 | 从语法基础逐步过渡到算法 | 基础篇、先修关系和结构化课程 |
| 洛谷学习 | 找到与当前知识点匹配的题目 | 题目元数据和洛谷跳转入口 |
| 错题复习 | 识别错误原因并安排二次练习 | 错因记录、二次练习和复习状态 |
| 多语言学习 | 使用自己熟悉的语言完成练习 | C、C++、Python 三种代码版本 |

#### 当前尚未覆盖的用户

项目当前只有学生端，尚未实现：

- 教师班级管理；
- 家长报告；
- 培训机构课程管理；
- 学校教务或竞赛队管理；
- 管理员内容审核后台。

因此，当前不宜将项目表述为“已经落地的教师 SaaS”或“学校教学管理平台”。

### 2.3 核心功能

#### 功能一：动态学习诊断

新用户注册后，需要完成一组学习诊断。诊断内容包括：

- 目标赛事或学习目标；
- 每周可投入时间；
- C 语言基础；
- 循环和数组等基础探测；
- 算法经验；
- 二分等专题理解；
- 常见卡点；
- 偏好的学习平台。

诊断问题具有一定的分支逻辑。例如：

- 用户在循环问题中表示困难，系统继续追问循环相关问题；
- 用户选择数组相关基础，系统追问数组边界问题；
- 用户表示做过二分题，系统继续询问二分答案中的具体卡点。

诊断结果会写入学习画像，并影响后续掌握度和推荐结果。

#### 功能二：目标驱动的每日计划

系统根据以下因素生成今日计划：

- 目标赛事；
- 目标日期；
- 每周学习时间；
- 当前水平；
- 诊断结果；
- 学习状态；
- 近期练习结果；
- 开放错题；
- 先修知识点掌握情况。

当前推荐评分的主要组成如下：

```text
推荐分数 =
    目标匹配度 × 35%
  + 掌握缺口 × 25%
  + 错题需求 × 20%
  + 截止日期压力 × 10%
  + 先修准备度 × 10%
```

计划还会根据每周时间和本周已经使用的学习时间计算今日学习预算，并限制每日最多推荐 4 个知识点。

#### 功能三：先修关系控制

部分进阶知识点需要先完成基础知识点。例如，系统可以在推荐进阶内容前检查：

- 前置知识点是否达到最低掌握度；
- 是否存在被阻塞的先修节点；
- 是否应该先复习基础内容。

当进阶节点暂时不适合学习时，系统会说明需要先完成哪些内容，而不是只返回一个模糊的“暂不可用”。

#### 功能四：结构化课程

课程页面目前包含以下教学环节：

1. 课前例题或承上启下检测；
2. 知识点速览；
3. 独立思考；
4. 问题与解题思路；
5. 分层提示、代码骨架和完整答案；
6. 易错点提醒；
7. 练习记录。

课程内容包含：

- 知识点摘要；
- 学习目标；
- 核心概念；
- 典型场景；
- 输入输出示例；
- 解题步骤；
- 思考方向；
- 代码提示；
- 待补全代码骨架；
- 完整参考答案；
- 反思问题；
- 常见错误。

> 注意：README 中仍有“四步法”表述，但当前界面实际包含课前检测加五个主要学习环节，活动材料发布前应统一文案。

#### 功能五：三语言代码版本

每个知识点提供：

- C 语言版本；
- C++ 版本；
- Python 版本。

用户可以在课程页切换语言，并下载对应的代码骨架文件：

- `.c`；
- `.cpp`；
- `.py`。

#### 功能六：洛谷练习入口

系统为知识点关联洛谷题目，并展示：

- 题号；
- 标题；
- 难度；
- 标签；
- 适配理由；
- 基础、巩固和挑战层级；
- 跳转洛谷按钮。

项目不抓取或保存洛谷完整题面、样例、解答和评测结果。系统只保存题目元数据和公开链接，题目内容与评测由洛谷提供。

#### 功能七：练习记录和错题闭环

用户完成练习后可以记录：

- 正确；
- 部分正确；
- 错误；
- 用时；
- 使用提示次数；
- 错误原因；
- 备注；
- 关联的洛谷题号。

错误原因包括：

- 读题错误；
- 建模错误；
- 算法错误；
- 复杂度错误；
- 实现错误；
- 调试困难；
- 其他。

当用户答错或部分正确时，系统会：

1. 更新该知识点掌握度；
2. 生成错题记录；
3. 生成针对性二次练习；
4. 提高该知识点后续推荐优先级；
5. 在错题解决前持续安排复习。

#### 功能八：学习报告

报告包括：

- 练习总数；
- 正确率；
- 待复习错题数；
- 最薄弱知识点；
- 高频错因；
- 下一步建议。

### 2.4 当前课程和数据规模

当前数据库和测试契约显示：

| 项目 | 数量或状态 |
|---|---:|
| 已发布知识点 | 40 个 |
| 基础篇 | 18 个 |
| 进阶篇 | 22 个 |
| 代码语言 | C、C++、Python |
| 代码版本 | 120 个 |
| 课前检测 | 40 条 |
| 先修关系 | 47 条 |
| 目标知识点权重 | 200 条 |
| 洛谷唯一题目元数据 | 27 道 |
| 知识点—题目关联 | 120 条 |

需要特别说明：洛谷题目关联数量不等于 40 个知识点都拥有独立、精细的人工选题。当前只有部分入门知识点在 JSON 文件中配置了专门题目，其他节点会按分类使用兜底题目。因此下一阶段需要补充教研审核和逐节选题。

### 2.5 产品价值

#### 对学生的价值

- 降低“今天学什么”的决策成本；
- 让学习计划适配目标、基础和时间；
- 将错题转化为下一步学习任务；
- 通过分层提示减少直接查看答案；
- 将课程、题目、错题和报告放在一个闭环内；
- 支持学生使用更熟悉的编程语言学习。

#### 对教师或教研人员的潜在价值

当前尚未实现教师端，但未来可以提供：

- 学生薄弱知识点分布；
- 班级学习进度；
- 错因统计；
- 竞赛备考路线；
- 课程完成情况和风险提醒。

这些属于后续产品方向，不应包装成当前已具备功能。

### 2.6 产品差异化

当前产品的差异化不在于“拥有最多题目”，而在于：

1. 将学习目标、时间预算和知识路线结合；
2. 将诊断、课前反馈和练习结果纳入推荐；
3. 将错因结构化，并影响后续计划；
4. 提供可解释的推荐理由；
5. 通过课程—洛谷—错题—报告形成闭环；
6. 使用本地优先架构，降低早期部署和隐私风险。

当前这些更接近“产品基础设施”，还不能直接称为行业壁垒。真正的长期壁垒需要来自：

- 真实学习行为数据；
- 高质量课程和题目教研；
- 被验证有效的推荐策略；
- 学生长期留存；
- 教师或机构的使用网络。

## 三、用户调研和测试证据

### 3.1 现有真实用户调研证据

目前仓库没有发现以下材料：

- 用户访谈记录；
- 问卷及原始数据；
- 可用性测试记录；
- 用户满意度或 NPS；
- 真实用户反馈；
- 留存数据；
- 学习完成率；
- 学习效果对照实验；
- 付费意愿测试。

因此，当前可以证明“系统已经实现并可运行”，但不能证明“系统已经被真实用户验证有效”。

### 3.2 本地数据库数据的正确解释

当前本地数据库大致包含：

| 数据表 | 数量 |
|---|---:|
| 学生账号 | 70 |
| 诊断会话 | 50 |
| 诊断答案 | 449 |
| 练习记录 | 87 |
| 错题 | 58 |
| 学习状态 | 60 |
| 技能掌握记录 | 750 |
| 今日推荐计划 | 16 |
| 洛谷练习进度 | 73 |

这些数据不能直接作为真实用户规模，原因是：

- 至少 57 个账号符合自动化测试中使用的 `u<时间戳>` 命名规律；
- 测试脚本会创建账号和练习记录；
- 测试结束后部分记录没有清理；
- 数据没有“真实用户/测试用户”标签；
- 多数记录集中产生于同一天。

正确表述应为：

> **本地数据库中存在工程调试和端到端测试产生的行为记录，但当前没有经过标注的真实用户样本，不能据此计算真实用户数、留存率或学习效果。**

### 3.3 自动化测试覆盖范围

仓库包含 9 个测试文件、23 个测试函数和约 221 条断言，覆盖：

- 注册、登录和 Cookie 会话；
- 动态诊断和诊断完成；
- 课程内容接口；
- 三语言代码版本；
- 先修关系无环；
- 目标分类和知识点体系；
- 洛谷题目目录；
- 洛谷题目打开和练习进度；
- 练习记录、错题和二次练习；
- 学习报告；
- 推荐预算和开放错题重复推荐；
- Serverless 数据库初始化；
- 前端关键交互和文案。

### 3.4 当前测试执行结果

在隔离的临时数据库中执行当前测试脚本时：

- 22 项测试通过；
- 1 项测试失败。

失败项为：

```text
test_frontend_mirrors_are_identical
```

失败原因是 `app/static/app.js` 与 `public/app.js` 不完全一致。CSS 和 HTML 镜像一致。

这意味着当前版本的技术验收状态应表述为：

> **主要后端和内容测试通过，但前端本地版与线上版存在同步问题，发布前应修复并重新执行完整测试。**

### 3.5 需要补充的真实用户验证

建议至少开展三类测试：

#### 访谈

目标：理解用户真实痛点和现有替代方案。

建议访谈 10–15 名学生，重点询问：

- 目前如何决定每天学什么；
- 如何选择课程、视频和题目；
- 错题是否会复习；
- 什么时候会放弃学习；
- 是否愿意使用自动推荐；
- 是否愿意为个性化计划付费。

#### 可用性测试

让用户完成以下任务：

1. 注册并完成诊断；
2. 找到今日推荐；
3. 学习一个知识点；
4. 打开分层提示；
5. 跳转洛谷题目；
6. 提交一道错误练习；
7. 在错题本中找到二次练习；
8. 查看学习报告。

需要记录：

- 完成率；
- 完成时间；
- 卡住的位置；
- 误解的文案；
- 用户主动提出的问题；
- 用户对推荐理由的信任程度。

#### 小规模留存测试

招募 30–50 名学生，连续使用 7–10 天，观察：

- 诊断完成率；
- 首次学习启动率；
- 首次练习完成率；
- D1、D3、D7 留存；
- 错题复习完成率；
- 计划执行率；
- 推荐接受率；
- 用户主动返回次数。

## 四、活动后 30 天计划

### 4.1 总目标

活动后 30 天不以新增大量功能为主，而以四个问题为核心：

1. 学生是否真正有“今天不知道学什么”的问题；
2. 推荐计划是否比固定顺序更容易执行；
3. 错题是否真正被复习；
4. 用户是否愿意持续使用并考虑付费。

### 4.2 分阶段计划

#### 第 1–3 天：工程稳定和发布准备

任务：

- 同步 `app/static` 和 `public` 前端文件；
- 修复前端镜像测试失败；
- 将测试数据库与开发数据库完全隔离；
- 统一“四步法”和实际课程步骤的文案；
- 为测试脚本增加数据清理或独立数据库配置；
- 检查线上 `SESSION_SECRET` 是否配置；
- 重新执行全部自动化测试；
- 建立版本号、变更记录和回滚方式。

交付物：

- 可重复部署的版本；
- 通过的测试报告；
- 发布检查清单；
- 已知问题列表。

#### 第 4–10 天：用户访谈和可用性测试

任务：

- 访谈 10–15 名目标学生；
- 完成至少 10 次任务型可用性测试；
- 观察用户完成诊断、课程和错题复习的过程；
- 记录用户是否理解“推荐理由”；
- 记录用户是否愿意打开代码骨架而不是直接看答案；
- 收集用户对学习时间预算的反馈。

交付物：

- 用户画像；
- 用户问题优先级；
- 高频卡点清单；
- 访谈原始记录和摘要；
- 首轮产品改进列表。

#### 第 11–20 天：产品和课程迭代

任务：

- 修复前三个最高频可用性问题；
- 重新审核 40 个知识点的课程内容；
- 为进阶知识点补充更精确的洛谷题目；
- 抽查 C、C++、Python 代码版本；
- 增加关键行为埋点；
- 记录推荐被接受、跳过和完成的原因；
- 增加真实用户和测试用户标识。

交付物：

- 第二个用户测试版本；
- 课程审核表；
- 题目映射审核表；
- 最小行为数据看板。

#### 第 21–30 天：小规模验证和商业测试

任务：

- 招募 30–50 名真实学生；

### 7.3 推荐算法

推荐引擎的主要输入包括：

- 目标赛事；
- 目标日期；
- 每周学习小时数；
- 当前学习水平；
- 知识点掌握度；
- 最近练习记录；
- 开放错题和到期复习记录；
- 前置知识点状态；
- 知识点目标权重。

系统会先为每个节点计算有效掌握度，再评估目标匹配度、基础缺口、错题需求、截止日期压力和先修状态，最后按分数排序，并在预算范围内选出最多 4 个项目。

### 7.4 部署方式

#### 本地部署

```text
Python 标准库后端
        ↓
SQLite 本地数据库
        ↓
浏览器访问 127.0.0.1:8080
```

#### 线上部署

```text
Vercel 静态前端
        ↓
Vercel Python Serverless Function
        ↓
Neon PostgreSQL
```

线上需要配置：

- `DATABASE_URL` 或 `POSTGRES_URL`；
- `SESSION_SECRET`。

### 7.5 已实现的安全措施

- PBKDF2-SHA256 密码哈希；
- 不保存明文密码；
- HMAC 签名会话；
- HttpOnly Cookie；
- SameSite Cookie；
- 8 小时会话有效期；
- 登录失败限流；
- 静态目录越界保护；
- `X-Frame-Options: DENY`；
- `X-Content-Type-Options: nosniff`；
- `Referrer-Policy`；
- 本地默认绑定 `127.0.0.1`；
- 不执行学生提交代码。

### 7.6 技术风险和待补工作

1. `app/static/app.js` 和 `public/app.js` 当前不一致，应建立自动同步或构建流程。
2. 线上必须使用随机 `SESSION_SECRET`，禁止使用开发默认值。
3. 进程内登录限流不适合多实例 Serverless，需要共享存储或边缘限流。
4. 尚需补充浏览器端端到端测试。
5. 尚需补充真实 PostgreSQL 环境测试。
6. C/C++ 代码需要编译测试，Python 代码需要运行测试。
7. 需要建立数据库备份、恢复和迁移机制。
8. 需要增加账号注销、数据导出和隐私同意流程。
9. 面向未成年人时，需要评估隐私、监护人同意和数据最小化要求。

## 九、演示和路演建议

### 9.1 三分钟演示故事

可以演示一个典型用户：

> 一名距离 CSP-J 还有 30 天、每周只能学习 5 小时、数组边界容易出错的学生。

演示步骤：

1. 注册账号；
2. 完成动态诊断；
3. 设定目标赛事、目标日期和每周时间；
4. 查看今日推荐和推荐理由；
5. 进入数组或基础算法课程；
6. 先完成课前检测；
7. 展示分层提示和代码骨架；
8. 跳转洛谷题目；
9. 记录一次“实现错误”；
10. 展示自动生成的二次练习；
11. 返回首页，展示错题重新进入今日计划；
12. 打开学习报告，查看薄弱点和下一步建议。

### 9.2 推荐的路演叙事

#### 开场问题

> 算法学习不缺题目、视频和题解，真正稀缺的是：面对一个具体学生，系统能否持续回答“今天该学什么、为什么学、做错之后下一步怎么办”。

#### 产品回答

> 竞途 AI 不是另一个题库，也不试图替代洛谷和 Bilibili。它是位于这些内容平台之上的算法学习调度层，把目标、时间、基础和每一次练习反馈编排成持续更新的学习路线。

#### 结尾表达

> **竞途 AI 的核心不是一次推荐，而是让学习行为持续改变下一次推荐。**

### 9.3 必须避免的表述

不要直接说：

- “已经有 70 名真实用户”；
- “已经证明能够提升成绩”；
- “接入了 GPT 自动答疑”；
- “自动同步洛谷账号成绩”；
- “每个知识点都有独立人工精选题库”；
- “已经落地学校或培训机构”；
- “已经实现稳定商业收入”。

更准确的替代表述是：

- “已有可运行 MVP”；
- “已建立端到端技术闭环”；
- “已完成自动化验收契约”；
- “下一阶段进行真实学生测试”；
- “当前使用规则推荐算法，后续评估引入大模型”；
- “正在验证学生持续使用和付费意愿”。

## 十一、最终结论

竞途 AI 当前最有价值的成果不是“使用了多少 AI 模型”，而是已经把算法学习中的多个断点连接起来：

```text
目标
  → 诊断
  → 学习计划
  → 课程
  → 洛谷练习
  → 错因
  → 复习
  → 报告
  → 下一次计划
```

项目的优势是闭环、可解释和本地优先；项目的短板是真实用户证据、内容教研深度、线上稳定性和商业验证不足。

最适合当前阶段的项目定位是：

> **竞途 AI 是一个面向算法竞赛入门学生的个性化学习规划与错题复习 MVP。它已经完成技术闭环，下一阶段将通过真实用户测试验证推荐有效性、学习留存和付费可能性。**
